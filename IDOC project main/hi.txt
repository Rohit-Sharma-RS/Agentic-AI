Detailed Step-by-Step Breakdown
Step 1: Customer Places a Purchase Order (EDI 850)
What happens: A buyer (e.g., Walmart) decides to order items and generates an EDI 850 Purchase Order document from their ERP system.
Payload data: Contains Buyer PO number, Order Date, Ship-to party address, Item numbers, Quantities, and Delivery dates.
Transport: Sent securely to your company’s network via AS2 or SFTP.
Step 2: Middleware Transformation & Routing
What happens: The middleware (SAP Integration Suite, SAP PO, MuleSoft, or Sterling) receives the raw EDI 850 file.
Mapping: The middleware maps the ANSI X12/EDIFACT fields into SAP’s standardized IDoc schema:
Customer PO Number $\rightarrow$ E1EDK01-BELNR
Customer Partner Number $\rightarrow$ E1EDKA1-PARTN
Material Number & Quantity $\rightarrow$ E1EDP01-MENGE & E1EDP19-IDTNR
Transmission: The middleware converts this to an IDoc structure and sends it to the SAP system via tRFC or HTTP(S).
Step 3: SAP Inbound Processing
Once the data lands in SAP, the IDoc passes through the internal ALE/IDoc engine:

Port Identification (WE21):
SAP receives the data packets via the configured RFC or XML port.
Control Record & Partner Profile Check (WE20):
SAP inspects the Control Record (EDI_DC40):
Sender Partner Number: Customer ID (e.g., CUST_1001)
Message Type: ORDERS
Basic Type: ORDERS05
SAP looks up transaction WE20 for partner CUST_1001. If ORDERS is configured, it identifies the inbound Process Code (typically ORDE).
Inbound Function Module Execution:
The Process Code ORDE triggers standard function module IDOC_INPUT_ORDERS.
The function module runs standard business logic (checks customer pricing, material availability, credit checks).
It calls the standard BAPI/transaction code (VA01) in the background to create the Sales Order.
📄 IDoc Structure in This Order Example
An IDoc consists of three structural layers:

Layer	Technical Name	Example Data in Inbound Order
Control Record	EDI_DC40	Direction: 2 (Inbound), Message Type: ORDERS, Partner: CUST_1001
Data Record	E1EDK01 (Header)	Customer PO: PO-987654, Currency: USD, Sales Org: 1000
 	E1EDKA1 (Partners)	Sold-to: 100025, Ship-to: 200050
 	E1EDP01 (Item 10)	Item: 000010, Quantity: 50 EA, Unit Price: $120.00
 	E1EDP19 (Material)	Customer Material: WIDGET-X $\rightarrow$ SAP Material: MAT-10023
Status Record	Status History	Tracked sequentially: 50 $\rightarrow$ 64 $\rightarrow$ 53
 

🚦 IDoc Status Lifecycle for Inbound Orders
When monitoring the transaction in BD87 or WE02 / WE05, the IDoc transitions through standard numeric statuses:

Status 50 — IDoc added to SAP database: SAP has received and saved the IDoc container.
Status 64 — IDoc ready to be passed for application: The IDoc is queued, awaiting the background job (RBDAPP01) or immediate processing.
Status 53 (Success) — Application document posted: The Sales Order is successfully created. The generated document number (e.g., Order #120045) is recorded in the status log.
Status 51 (Error) — Application document not posted: Failed due to a business or configuration error (e.g., material blocked, missing price, invalid ship-to address). Can be reprocessed in BD87 after resolution.
🔄 Outbound Follow-up: Order Confirmation (ORDRSP)
To complete the loop, once the sales order is successfully generated in SAP:

SAP generates an Outbound IDoc of message type ORDRSP (Order Response).
The IDoc passes through statuses 01 (Created) $\rightarrow$ 30 (Ready for dispatch) $\rightarrow$ 03 (Passed to port).
The middleware translates the ORDRSP into an EDI 855 (Purchase Order Acknowledgment) and delivers it back to the customer.
